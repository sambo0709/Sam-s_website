EventFlow — Workout Tracking API

EventFlow is a production-ready backend REST API built with Spring Boot, MongoDB, and Apache Kafka. It manages user workout sessions with full CRUD support, a polymorphic exercise model, and real-time event streaming — firing a Kafka message every time a workout is saved so downstream services can react instantly. The project is fully tested with JUnit 5 and Mockito and containerized with Docker for local development.

Technologies Used

  • Java 17 + Spring Boot 3.2 — REST controllers, service layer, dependency injection
  • MongoDB — document storage via Spring Data repositories
  • Apache Kafka — event streaming with a producer/consumer pipeline
  • JUnit 5 + Mockito — unit and integration testing
  • Docker — containerized MongoDB and Kafka for local development
  • Maven — build and dependency management
  • Jakarta Validation — request body validation with constraint annotations

Features

  • Full CRUD REST API for users and workouts (POST, GET, DELETE)
  • Polymorphic exercise model — CardioExercise and StrengthExercise share an abstract base with separate calorie calculation logic
  • Kafka producer fires a WORKOUT_SAVED event after every successful workout write
  • Kafka consumer receives and processes workout events for downstream handling
  • Global exception handling via @RestControllerAdvice with structured error responses
  • Input validation on all request bodies using Jakarta Bean Validation
  • 15+ unit and integration tests covering service layer, domain logic, and edge cases

Technical Architecture

The project follows a layered microservices-style architecture. REST controllers handle incoming HTTP requests and delegate to the service layer, which contains all business logic. Repositories abstract MongoDB access using Spring Data. When a workout is successfully persisted, the WorkoutService calls the Kafka producer to publish a WORKOUT_SAVED event to the workout-events topic. The consumer listens on the same topic and processes events independently — decoupling the write path from any downstream logic like notifications or analytics. 

Client
  └── REST Controllers (UserController, WorkoutController)
        └── Service Layer (UserService, WorkoutService)
              ├── MongoDB Repositories
              └── Kafka Producer → workout-events topic → Kafka Consumer

The exercise model uses Jackson's @JsonSubTypes for polymorphic deserialization — a single exercises array in the workout payload can contain a mix of cardio and strength objects, each deserializing into the correct subclass automatically.

API Endpoints

Users

  • POST /api/users — create a user profile
  • GET /api/users/{id} — get user by ID
  • GET /api/users — get all users
  • DELETE /api/users/{id} — delete a user

Workouts

  • POST /api/workouts — create a workout and fire Kafka event
  • GET /api/workouts/{id} — get workout by ID
  • GET /api/workouts/user/{userId} — get all workouts for a user
  • DELETE /api/workouts/{id} — delete a workout

Kafka Event Flow

Every POST /api/workouts request that successfully writes to MongoDB triggers the Kafka producer to publish the following message to the workout-events topic: 

{
  "event": "WORKOUT_SAVED",
  "workoutId": "69e5c0fb1e69a22f74d7299e",
  "userId": "69e5bf581e69a22f74d7299c"
}

The consumer listens on the same topic and logs the event — in a production system this would trigger push notifications, update analytics dashboards, or sync external fitness platforms.

Testing

The test suite uses JUnit 5 with Mockito for mocking dependencies, keeping tests fast and isolated without requiring a running database or Kafka broker. Key test cases include:

  • Creating a workout verifies the Kafka producer fires exactly once after save
  • Creating a workout for a non-existent user throws ResourceNotFoundException and does not publish a Kafka event
  • Calorie calculations verified for both CardioExercise and StrengthExercise formulas
  • StatsService generic average and max operations tested with integer and double lists
  • Edge cases — null lists, empty lists, zero/negative durations — all tested with assertThrows

What I Learned

Building EventFlow gave me hands-on experience with the full Spring Boot ecosystem — from wiring up repositories and service beans to configuring Kafka topics and writing idiomatic REST controllers. Integrating Kafka taught me how to decouple writes from downstream processing using event-driven patterns, and how the producer/consumer lifecycle works in a Spring application. Writing the Mockito test suite reinforced the importance of verifying not just return values but side effects — confirming that Kafka fires after a successful save but not after a failed one was one of the more satisfying tests to write.
